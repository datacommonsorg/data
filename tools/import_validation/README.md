# Import Validation Framework

This document describes how to use the Import Validation Framework to run a series of automated checks on data imports.

## Overview

The framework is designed to be a flexible and extensible tool for ensuring the quality and consistency of data before it is imported. It operates on summary files generated by other import tools, such as a statistics summary and a differ output summary.

At a high level, the framework:

1. Loads the validation configuration and input artifacts.
2. Selects the enabled rules and applies any configured scope.
3. Runs each recognized validator and records one result per rule.
4. Writes the rule results to a CSV or JSON report when at least one recognized, enabled rule runs.
5. Returns an overall success value that is true only when every executed rule passes.

The framework produces validation results; it does not assign auto-refresh candidate statuses such as `STAGING`, `SKIP`, or `VALIDATION`. The auto-refresh executor consumes the overall validation result and owns that classification.

## Running the Framework

The main entry point for the framework is `runner.py`. It is a command-line tool that takes a configuration file and the paths to the summary data files as input.

### Usage

```bash
python3 -m tools.import_validation.runner \
    --validation_config=<path_to_your_config.json> \
    --stats_summary=<path_to_your_stats_summary.csv> \
    --lint_report=<path_to_your_report.json> \
    --differ_output=<path_to_your_differ_output_directory> \
    --validation_output=<path_for_your_output.csv>
```

- `--validation_config`: Path to the JSON file that defines which validations to run.
- `--stats_summary`: Path to the CSV file containing summary statistics of the import (e.g., `summary_report.csv`).
- `--lint_report`: Path to the GenMCF JSON report (normally `report.json`).
- `--differ_output`: Path to the differ output directory containing `differ_summary.json` and node-diff MCF files.
- `--validation_output`: Path where the output report of the validation will be saved. The file extension (`.csv` or `.json`) determines the output format.

The script exits with status code `1` if any executed rule returns `FAILED`, `CONFIG_ERROR`, or `DATA_ERROR`, and `0` when every executed rule returns `PASSED`.
If no recognized, enabled rule executes, the script exits with status code `0`
without creating the `--validation_output` file.

### Input Artifacts and Logical Sources

Validators use logical sources loaded from the input artifacts:

| Logical Source | Input Artifact | Used By |
| --- | --- | --- |
| `stats` | `summary_report.csv` | Date, place, observation, unit, value, golden, and SQL validations |
| `lint` | GenMCF `report.json` | Empty-import, missing-reference, and lint-error validations |
| `differ_summary` | `<differ_output>/differ_summary.json` | Deleted-record count and percentage validations |
| `differ` | `<differ_output>/nodes-added.mcf`, `nodes-deleted.mcf`, and `nodes-modified.mcf`, aggregated by StatVar | Added-record, modified-record, and SQL validations |

The import tool owns the complete `summary_report.csv` and `report.json` formats. See `<IMPORT_REPO>/docs/usage.md` for their generation and format. The import differ owns the differ artifacts; see [the import differ documentation](../import_differ/README.md).

## Configuration

The behavior of the validation framework is controlled by a JSON configuration file. This file uses a structured schema to define a series of validation rules.

### Top-Level Structure

The configuration is a JSON object with these top-level fields:

- `schema_version`: The version of the configuration schema (e.g., "1.0").
- `definitions`: Optional reusable definitions, including named scopes.
- `rules`: A list of validation rule objects to be executed.

```jsonc
{
    "schema_version": "1.0",
    "rules": [
        // Add validation rules here.
    ]
}
```

This example uses a comment for illustration. Remove comments before saving
the JSON configuration.

### Rule Definition

Each object in the `rules` list defines a single validation check with the following keys:

- `rule_id`: A unique, human-readable identifier for the rule.
- `validator`: The name of the validator to execute (see the table below for supported validators).
- `description`: An optional human-readable description.
- `enabled`: An optional boolean that controls whether the rule runs. It defaults to `true`.
- `scope`: An optional object, or a named scope reference such as `@population_scope`, that defines the data to be validated.
- `params`: An optional dictionary of parameters to pass to the validator.

For default rules, import-specific overrides, merge behavior, and advanced configuration, see [Validations.md](Validations.md).

### Scoping and Filtering

The `scope` object specifies which data to run the validation on. It has two main parts:

- `variables`: An optional filter to select a subset of StatVars from the data source.

The `variables` object can contain any of the following keys:

- `dcids`: A list of exact StatVar DCIDs to select.
- `regex`: A list of regular expressions to match against StatVar DCIDs.
- `contains_all`: A list of substrings that must all be present in the StatVar DCID.

**Note:** When multiple filter types are provided (`dcids`, `regex`, `contains_all`), the results are combined with a logical OR (union).

A reusable scope can instead be declared under `definitions.scopes` and referenced by name with an `@` prefix.

### Example Configuration

Here is an example of a complete configuration file:

```json
{
    "schema_version": "1.0",
    "rules": [
        {
            "rule_id": "check_latest_date_for_all",
            "validator": "MAX_DATE_LATEST",
            "params": {}
        },
        {
            "rule_id": "check_deleted_points_threshold",
            "validator": "DELETED_RECORDS_PERCENT",
            "params": {
                "threshold": 1
            }
        },
        {
            "rule_id": "check_percent_max_value",
            "validator": "MAX_VALUE_CHECK",
            "scope": {
                "variables": {
                    "contains_all": ["Percent"]
                }
            },
            "params": {
                "maximum": 100
            }
        }
    ]
}
```

### Advanced Validation with `SQL_VALIDATOR`

For complex validation scenarios that require aggregations, joins, or multi-column filtering, the framework provides the powerful `SQL_VALIDATOR`. This allows you to define a custom validation using a SQL query.

The validator uses two parameters:
- `query`: A standard SQL `SELECT` statement that defines the precise dataset to be validated. The `stats_summary` data is available as the `stats` table, and the `differ_output` is available as the `differ` table.
- `condition`: A SQL boolean expression that must evaluate to `TRUE` for every row returned by the `query`.

The framework executes the `query` and then finds all rows from the result that do **not** meet the `condition`. If any such rows are found, the validation fails, and the failing rows are included in the output report.

#### SQL Validator Example

**Rule:** "For all StatVars that are percentages, the `MaxValue` must be less than or equal to 100."

```json
{
    "rule_id": "check_max_value_for_percent_svs_sql",
    "validator": "SQL_VALIDATOR",
    "params": {
        "query": "SELECT StatVar, MaxValue, Units FROM stats WHERE Units = 'Percent'",
        "condition": "MaxValue <= 100"
    }
}
```

### Supported Validations

The following validations are currently supported:

| Validator Name | Description | Source and Fields Used | `params` Configuration |
| --- | --- | --- | --- |
| `SQL_VALIDATOR` | Runs a user-defined SQL query to perform complex validations. | Available SQL tables: `stats` and `differ`; the query determines which tables and fields are used | `query` (string), `condition` (string) |
| `EMPTY_IMPORT_CHECK` | Checks whether both the generated-node and processed-row counts are zero. | `lint`; `NumNodeSuccesses`, `NumRowSuccesses` | None |
| `MAX_DATE_LATEST` | Checks that the latest date in the data is from the current year. | `stats`; `MaxDate` | None |
| `MAX_DATE_CONSISTENT` | Checks that the latest date is the same for all StatVars. | `stats`; `MaxDate` | None |
| `MISSING_REFS_COUNT` | Checks that the total number of missing references is within a threshold. | `lint`; warning counters prefixed with `Existence_MissingReference` | `threshold` (number, defaults to 0) |
| `LINT_ERROR_COUNT` | Checks that the total number of lint errors is within a threshold. | `lint`; all error counters | `threshold` (number, defaults to 0) |
| `DELETED_RECORDS_COUNT` | Checks that the total number of deleted observation points is within a threshold. | `differ_summary`; `deleted_obs_count` | `threshold` (number, defaults to 0) |
| `DELETED_RECORDS_PERCENT` | Checks that the percentage of deleted observation points is within a threshold. | `differ_summary`; `deleted_obs_count`, `previous_obs_count` | `threshold` (number, defaults to 0) |
| `MODIFIED_RECORDS_COUNT` | Checks that the number of modified points is the same for all StatVars. | `differ`; `StatVar`, `MODIFIED` | None |
| `ADDED_RECORDS_COUNT` | Checks that the number of added points is the same for all StatVars. | `differ`; `StatVar`, `ADDED` | None |
| `NUM_PLACES_CONSISTENT` | Checks that the number of places is the same for all StatVars. | `stats`; `StatVar`, `NumPlaces` | None |
| `NUM_PLACES_COUNT` | Checks that the number of places is within a defined range. | `stats`; `StatVar`, `NumPlaces` | `minimum`, `maximum`, or `value` (number) |
| `NUM_OBSERVATIONS_CHECK` | Checks that the number of observations is within a defined range. | `stats`; `StatVar`, `NumObservations` | `minimum`, `maximum`, or `value` (number) |
| `UNIT_CONSISTENCY_CHECK` | Checks that the unit is the same for all StatVars. | `stats`; `StatVar`, `Units` | None |
| `MIN_VALUE_CHECK` | Checks that the minimum value is not below a defined minimum. | `stats`; `StatVar`, `MinValue` | `minimum` (number, required) |
| `MAX_VALUE_CHECK` | Checks that the maximum value is not above a defined maximum. | `stats`; `StatVar`, `MaxValue` | `maximum` (number, required) |
| `GOLDENS_CHECK` | Verifies that the data contains all records defined in a golden set. | `stats` is required by the runner; `input_files` optionally supplies the records compared with the goldens | `golden_files` (required), `input_files`, `goldens_key_property` |

For more details on the validations, please refer to [Validations.md](Validations.md)

## Output

When at least one recognized, enabled rule executes, the framework generates a
report file specified by `--validation_output`. The file extension (`.csv` or
`.json`) determines the report format. If no recognized, enabled rule executes,
the framework does not create a report file.

### CSV Output

If the output path ends with `.csv`, the file will contain the following columns:

- `ValidationName`: The unique ID of the rule that was run.
- `Status`: The result of the validation (`PASSED`, `FAILED`, `CONFIG_ERROR`, or `DATA_ERROR`).
- `Message`: A human-readable message describing the outcome.
- `Details`: A validator-specific JSON string containing structured evidence. It has no universal schema.
- `ValidationParams`: A JSON string of the parameters that were passed to the validator.

### JSON Output

If the output path ends with `.json`, the file will be a JSON array where each object represents a validation result with the following keys:

- `validation_name`: The unique ID of the rule that was run.
- `status`: The result of the validation.
- `message`: A human-readable message describing the outcome.
- `details`: A validator-specific object containing structured evidence.
- `validation_params`: An object containing the parameters that were passed to the validator.

Use `Message` for a quick explanation and `Details` for structured diagnostic evidence. To interpret `Details`, match `ValidationName` to the rule's `rule_id`, identify its `validator`, and consult that validator's behavior.
